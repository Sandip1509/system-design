The framework: RADIO

Say the order out loud before you start — it buys you structure the interviewer can follow.

Every "design X" interview rewards the same five moves, in the same order. For TinyURL they map cleanly:

R — Requirements

Functional + non-functional. Ask before you assume.

A — API + estimation

Shape the interface, then size the traffic and storage it implies.

D — Data model

Tables, keys, and which store fits the access pattern.

I — Implementation

The algorithm (short-code generation) and the high-level architecture.

O — Optimize

Cache, shard, replicate, harden — then handle the curveballs.

Why this order Interviewers are grading how you think, not whether you land on the "correct" architecture. Narrating RADIO out loud turns 40 minutes of silence-then-a-diagram into a conversation they can steer — which is what they're actually evaluating.
01

Clarify requirements

Two minutes of questions here prevents twenty minutes of designing the wrong system.

Split the board in two — functional and non-functional — and ask before assuming either column.

The number that drives everything downstream 62⁷ ≈ 3.5 trillion is comfortably above the 500 billion URLs you'll ever need — that's why a 7-character base62 code is the answer, and it's why you can say it with confidence instead of guessing at length.
03

API design

Three endpoints cover the whole surface area. Sketch them before the data model — the model falls out of the response shape.

EndpointBody / paramsReturns
POST /api/v1/shorten{ longUrl, customAlias?, ttl? }201 { shortUrl }
GET /{shortCode}—301/302 → longUrl
GET /api/v1/{shortCode}/stats—200 { clicks, createdAt, ... }
DELETE /api/v1/{shortCode}auth token204

Say out loud: idempotency matters on POST /shorten — if the same long URL is submitted twice without a custom alias, decide (and state) whether you return the existing short code or mint a new one. Either is defensible; having an opinion is what's graded.

Data model

One table, one obvious index, and a deliberate choice of store.

├─ created_at   TIMESTAMP
├─ expires_at   TIMESTAMP    NULL
└─ click_count  BIGINT       DEFAULT 0     -- or move to a separate analytics store

users
├─ user_id      BIGINT PRIMARY KEY
└─ email        VARCHAR
ChoiceSQL (Postgres/MySQL)NoSQL (DynamoDB/Cassandra)
Access pattern fitFine — access is by primary key, joins are rareExcellent — pure key→value lookup, no joins ever needed
ScaleNeeds manual sharding past a pointScales horizontally by design
RecommendationNoSQL key-value store — the workload is a key lookup at massive scale with no relational queries; that's exactly what wide-column/KV stores are built for.
05

Short-code generation

The one algorithmic decision the whole interview hinges on. Know two approaches and argue for one.

The short code is a base62 string (a–z A–Z 0–9, 62 symbols). The question is how you pick the underlying number before encoding it.

Recommendation to state out loud Go with range-based counters: each app server checks out a batch of IDs (e.g. 1,000) from a lightweight coordinator (Zookeeper/etcd/a Postgres row with UPDATE ... RETURNING) and hands them out from memory. It's simpler under load than hash-and-retry, guarantees no collisions, and the coordinator is a tiny, easy-to-replicate piece of state.

Read path vs. write path

Walk both explicitly — they touch the same boxes in a different order, and the read path is the one that has to be fast.

08

Scaling & caching

Reads outnumber writes 100:1 — every lever here exists to keep the cheap path cheap.

Cache-aside + LRU

Redis in front of the DB; evict least-recently-used. Hot links (viral posts) stay resident, cold ones age out.

DB sharding

Shard by hash(short_code) mod N — even distribution, and lookups are always single-shard since you always have the key.

Read replicas

Even sharded, add replicas per shard for read throughput; writes go to primary, reads fan out.

CDN / edge redirect

For read-heavy public links, cache the 301 at the edge (CDN) so popular redirects never reach your origin at all.

A number worth stating If Redis holds keys for the hottest ~20% of links and that 20% accounts for ~80% of traffic (it will — link popularity is heavily skewed), a cache sized for a few GB of hot keys can absorb the vast majority of your 40,000 reads/sec peak.
09

301 vs. 302: the tradeoff they want you to name

A small HTTP detail that's a favorite because it has a real, statable tradeoff.

301 Moved Permanently302 Found (temporary)
Browser behaviorCaches the redirect locallyNever caches; always re-asks your server
Server loadLower — repeat visits skip your server entirelyHigher — every click hits your redirect service
Click analyticsBroken — cached clicks never reach youAccurate — you see every click
Use whenYou don't need per-click analyticsAnalytics is a stated requirement
The line to say "Since analytics is in scope, I'll use 302 — the extra origin traffic is exactly the price of seeing every click, and it's the reason the read path has to stay this cheap."
10

Analytics, kept off the hot path

The rule: nothing that isn't required to answer the redirect gets to add latency to it.

The app server fires a small event (short_code, timestamp, referrer, coarse geo/IP) onto a queue and returns the redirect immediately — it does not wait for that write to land anywhere. A separate consumer batches events into an analytics store (a column store or a time-series DB, not the primary URL table) for later aggregation into click counts and dashboards.

redirect_handler(short_code):
    long_url = cache_or_db_lookup(short_code)
    queue.publish_async({code: short_code, ts: now(), ref: referrer})  # fire-and-forget
    return HTTP 302 Location: long_url  # doesn't wait on the line above
11

Edge cases worth raising unprompted

Bringing these up yourself, briefly, signals seniority — you don't need to solve all of them deeply.

Custom alias collides with an existing code
Check existence on write (this path can afford the extra round-trip, it's rare and user-facing); return 409 if taken.
Link expiration & cleanup
Store expires_at; check it lazily on read (cheap, no extra job) and run an offline batch job to reclaim expired rows and free their short codes.
Rate limiting / abuse
Token-bucket limiter per API key/IP at the load balancer or API gateway, ahead of the app servers — stop abuse before it costs you compute.
Malicious / phishing URLs
Check submitted long URLs against a safe-browsing blocklist (e.g. Google Safe Browsing API) at write time, and periodically re-scan stored URLs since a benign site can turn malicious later.
Key-gen coordinator range handoff
If a server crashes mid-range, those few unused IDs are simply lost — that's fine, the key space (3.5 trillion) is orders of magnitude larger than you'll ever need.
Sequential / guessable IDs
If codes are assigned from a monotonic counter, don't base62-encode it verbatim — shuffle bits or XOR with a fixed mask first, so short codes aren't trivially enumerable.
12

Curveball follow-ups

Interviewers reuse these because each one tests whether your design was principled or memorized.

"Your cache node just died — what happens?"
Reads fall through to the DB (higher latency, not an outage) until the node — or its replica — is back; this is exactly why cache-aside is safer here than a write-through cache you'd depend on for correctness.
"How do you avoid two servers handing out the same ID?"
The coordinator hands out non-overlapping ranges atomically (a single row update with RETURNING, or a Zookeeper znode); two servers can never be assigned the same range.
"What if one shard gets a disproportionate share of traffic?"
Hashing the short code (not the long URL, not sequential ranges) distributes load evenly — a hot individual link is absorbed by the cache layer before it ever reaches the shard.
"How would you support a custom domain per customer?"
Add a domain column and make the composite (domain, short_code) the lookup key; the redirect service resolves the incoming Host header first.
"Design it for strong consistency instead."
State the cost plainly: you'd move from an eventually-consistent cache/replica setup to synchronous replication or a consensus store, trading availability and latency for guaranteed-fresh reads — and that trade is usually the wrong one for a redirect service.

The 40-minute script

A pacing guide, not a transcript — adapt the minutes to how much the interviewer wants to dig into any one step.

  1. 0–5 min — Ask the requirements questions from step 01. Write functional / non-functional on the board.
  2. 5–10 min — Estimate traffic and storage (step 02). State the 62⁷ key-space number out loud.
  3. 10–15 min — Sketch the API (step 03) and the single-table data model (step 04).
  4. 15–22 min — Present the short-code generation tradeoff (step 05) and commit to range-based counters.
  5. 22–30 min — Draw the high-level architecture (step 06), then narrate the write and read paths separately (step 07).
  6. 30–36 min — Scaling levers (step 08): cache-aside, sharding, replicas, CDN. Land the 301-vs-302 call (step 09) and the async analytics pipeline (step 10).
  7. 36–40 min — Volunteer two edge cases (step 11) before they're asked, and leave room for follow-ups (step 12).
Reference notes for interview prep — not a production spec. Numbers throughout are illustrative back-of-envelope estimates.
